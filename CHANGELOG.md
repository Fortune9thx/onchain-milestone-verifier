# Changelog

All notable changes to this project are documented in this file.

## [1.2.0] - 2026-08-25

A second maximally adversarial review, run the same way as the one that produced 1.1.0 (source code only, no design docs consulted), found that two of 1.1.0's own fixes had traded one real problem for another. Both are fixed here; the second is the more serious of the two.

- **Critical, fixed:** `retry_release` (added in 1.1.0 to fix a real reconciliation gap) had no cap and no accompanying state mutation — every other fund-moving method in this contract changes some piece of state specifically to block re-entry (`verify_milestone`'s status flip, `withdraw_unallocated`'s balance decrement), but `retry_release` was the one exception. Since this contract pools all programs' escrowed GEN in a single contract balance with no on-chain segregation, an unbounded `retry_release` meant any grantee whose tranche had ever legitimately released could call it in a loop and drain GEN belonging to entirely unrelated programs, not just their own tranche's allocation. Fixed by adding `release_retry_count` (tracked on the tranche, incremented and written *before* the transfer, matching this contract's checks-effects-interactions convention) capped at `MAX_RELEASE_RETRIES` (1) — this is now the one method whose repeat-call safety comes from an explicit counter rather than a natural state transition, and it is capped accordingly.
- **High, fixed:** `MAX_VERIFICATION_ATTEMPTS_PER_TRANCHE` (1.1.0's fix for unlimited free re-verification) was a fixed, permanent, shared count — closing the original farming vector but opening a new one: a bad-faith funder, equally entitled to call `verify_milestone`, could exhaust the shared budget on genuinely honest, early, not-yet-satisfied readings before the grantee ever got a chance to prove real completion, then reclaim the entire allocation via `reclaim_stale_tranche`'s unrelated 90-day timeout — denying a grantee who actually finished. Replaced the fixed count with `MIN_VERIFICATION_INTERVAL_SECONDS` (24 hours), a cooldown between consecutive attempts on the same tranche. A cooldown bounds the *rate* of re-rolling a stochastic judgment (closing the original vulnerability) without ever creating a hard ceiling a bad-faith party can run out the clock on — `STALE_TRANCHE_TIMEOUT_SECONDS` remains the only outer bound on how long any of this can take, exactly as it already was everywhere else in this contract.
- Test suite grew from 42 to 44 direct-mode tests (2 removed for the now-obsolete count cap, 5 added for the cooldown and retry-cap behavior); `genvm-lint check`/`validate` both still clean.

See `docs/DESIGN.md` §13 for the full account of both findings and why the specific replacement mechanisms were chosen.

## [1.1.0] - 2026-08-23

A maximally adversarial post-launch review (source code only, no design docs consulted, in the style of a strict GenLayer Portal reviewer) surfaced five findings against the deployed 1.0.0 contract. All five are fixed in this revision; none required an interface-breaking change beyond the addition of `retry_release`. Redeployed to Bradbury at `0xDe1817Aa376Dc25cC2dF36a0738a615E1B215836` (deploy tx `0x4a979ae61361e4802bd3fc54ec6c8132e9f99f008a95bb57c4ca6db74f35f032`, confirmed `FINALIZED`/`AGREE`/`FINISHED_WITH_RETURN`, 5/5 validators agreed, post-deploy read confirmed). The 1.0.0 address below is superseded — see FINAL_CHECKLIST.md.

- **Critical (fund-drain risk), fixed:** `verify_milestone` had no limit on re-triggering the same tranche's judgment round. Because the judgment is a real LLM call and `gl.eq_principle.strict_eq` only guarantees agreement *within* a round (not across separately-triggered rounds over the same unchanged state), an attacker could spam-retry a genuinely-unmet milestone at gas cost alone, hoping one round's independent judgments happened to land on an unwarranted `SATISFIED` — an asymmetric bet against the full tranche amount. Fixed with two gates, both enforced before any LLM call or storage write: (1) a fresh attempt's observed-state hash must differ from the tranche's last attempt (`tranche.last_verification_marker`); (2) total attempts per tranche are hard-capped at `MAX_VERIFICATION_ATTEMPTS_PER_TRANCHE` (5) regardless of state-change, closing the loophole where a target contract's own operator could oscillate its state to keep re-arming gate (1).
- **High, fixed:** the same missing rate-limit let `tranche_verification_ids` (and the `verifications` map) grow without bound under spam, with a full read-modify-write JSON re-encode on every append. Closed by construction once gate (1)/(2) above block spam attempts before they ever write.
- **High, fixed:** fund release was push-only (`emit_transfer`, async, no on-chain delivery confirmation available to contract code) with no reconciliation path if a transfer never arrived. Added `retry_release(tranche_id)`, a funder-or-grantee-callable manual escape hatch that re-issues the transfer for an already-`RELEASED` tranche without touching accounting. Documented, not hidden: calling it after a transfer that actually succeeded sends a genuine duplicate payment — GenVM exposes no delivery receipt this contract could check instead.
- **Medium, fixed:** the module docstring and README overclaimed support for "ANY view method" on a target contract; `_validate_view_args` has always only accepted `str`/`int`/`bool` arguments, with no coercion for `Address`/`bytes`/nested arguments. Corrected the claim in both places rather than expanding scope same-day.
- **Medium, fixed:** `_stringify_view_result`'s per-level depth/item caps bounded output size but not total recursive work — a wide-and-deep adversarial return value could still multiply per-level caps combinatorially. Added `MAX_OBSERVED_STATE_NODES`, a hard ceiling on total nodes visited across the whole traversal.
- Test suite grew from 36 to 42 direct-mode tests covering all five fixes; `genvm-lint check`/`validate` both still clean.

## [1.0.0] - 2026-08-23

Initial release. Deployed to Bradbury at `0xF5Df96807a6c71b273F361633d19529c8B7918e7` and live-verified end-to-end with a real 2 GEN escrow (`create_program` → `register_tranche` → `verify_milestone` → `NOT_SATISFIED` → target `mark_live()` → `verify_milestone` → `SATISFIED` → 1 GEN released).

- `create_program(grantee)` — payable, escrows GEN for a grantee.
- `register_tranche(program_id, amount, milestone_description, target_contract, view_method, view_args_json)` — funder-only, registers a milestone-gated tranche against a program's unallocated escrow.
- `verify_milestone(tranche_id)` — deterministic cross-contract read (`.view(state=StorageType.LATEST_FINAL)`) against the target contract, followed by an independent `gl.eq_principle.strict_eq` judgment (`SATISFIED`/`NOT_SATISFIED`/`INSUFFICIENT_STATE`); releases escrowed GEN to the grantee only on `SATISFIED`. A failed or null-returning read short-circuits to `INSUFFICIENT_STATE` without spending an LLM call.
- `withdraw_unallocated(program_id)` — funder-only, refunds never-allocated escrow.
- `reclaim_stale_tranche(tranche_id)` — funder-only, after a fixed 90-day timeout with no successful verification, reclaims a tranche's allocation.
- Full view surface: `get_program`, `get_tranche`, `get_verification`, `list_program_ids`, `list_tranche_ids`, `list_verification_ids`, `list_tranches_for_grantee`, `get_program_count`.
- 36 direct-mode tests, including a project-specific `_gl_call_hook`-based mock for cross-contract calls (no built-in `gltest` support exists for this); `genvm-lint check`/`validate` both clean.
- A real bug found and fixed during development: a failed cross-contract read does not raise an exception (the installed SDK's `gl_call_generic` returns `None` on failure) — the original `try/except`-only detection missed this, caught by the test suite before deployment. See `docs/DESIGN.md` §9.
- A second real finding, surfaced only by the live deployment itself: querying `LATEST_FINAL` state against a target contract that has been `ACCEPTED` but not yet `FINALIZED` is a VM-level fault, not a catchable Python exception — the whole transaction reverts before any of `verify_milestone`'s own error handling can run. This is an operational sequencing constraint for integrators (wait for the target's write to finalize before verifying against it), not a code defect; documented in `docs/DESIGN.md` §9a.
- CI workflow running lint (check + validate) and tests on every push.
